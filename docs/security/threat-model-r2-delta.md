# Threat-model delta — R2 surfaces (SaaS accounts, billing, batches, LNURL, exports)

*Status: author's analysis of code on branch `claude/busy-goodall-ajeb0p`. Extends `threat-model.md`. **No human security review or penetration test has been done**, and none of the new surfaces has been exercised by anyone other than this repository's tests. Test names refer to `apps/api/test/{saas,lnurl,security,lnd}.itest.ts`.*

## New assets
Account credentials and sessions · single-use e-mail/reset/invite tokens · TOTP secrets and recovery material · billing-provider webhook secret and API key · subscription/entitlement state (it decides what a paying customer may do) · exported reports and payout CSVs (contain payee identifiers) · support tickets.

## New trust boundaries
Browser ⇄ API (account lifecycle) · API ⇄ mail provider (Resend or outbox) · billing provider ⇄ API webhook · API ⇄ **arbitrary third-party LNURL servers (untrusted)** · operator-supplied CSV ⇄ API · API ⇄ analytics store.

| Surface | Threat | Mitigation in code | Evidence | Residual / not done |
|---|---|---|---|---|
| E-mail verification, password reset, invitations | token theft/guessing, replay, enumeration | random raw token, only its hash stored; single-use `UPDATE … WHERE used_at IS NULL AND expires_at > now()`; TTLs 48 h verify / 1 h reset / 7 d invite; reset responds identically for unknown addresses | `saas.itest` (account lifecycle block) | **Mail is delivered to an outbox unless a provider key is configured; real delivery (SPF/DKIM/DMARC, bounce handling) is not commissioned.** Tokens appear in URLs and so in browser history/referrers on the verification page |
| Sessions / account closure | stale sessions after reset or closure | all sessions revoked on password reset, member revocation and account closure (closure also revokes API keys created by the user) | `saas.itest` | no device-management UI beyond revoke-all; no suspicious-login alerts |
| MFA (TOTP) | stolen password/session approves money | TOTP enrolment (secret encrypted at rest); **for users who enabled MFA, a current code is required at sign-in, on approve and on execute** | `saas.itest` (MFA step-up), `adversarial.itest` | TOTP only: no WebAuthn. **MFA is opt-in per user — there is no organisation or plan policy that forces it**, so a privileged user without MFA enabled gets no step-up. Approval signing key still lives in browser storage |
| Billing webhooks | forged/replayed/out-of-order event grants or revokes entitlements | provider signature verified over the **raw body** (Stripe `t=…,v1=` HMAC-SHA256 with 5-minute tolerance; Paystack `x-paystack-signature` HMAC-SHA512), constant-time compare; `billing_events` unique `(provider, event_id)` → duplicates answer 200 with no effect; events older than the last applied one are recorded `stale`; sandbox provider is **refused in production** | `saas.itest` (signatures, duplicates, stale ordering, production refusal) | **Signature schemes were implemented from provider documentation and tested against locally computed signatures, not against live provider traffic.** `docs/business/billing-provider-evaluation.md` found five mapping errors (Stripe basil field moves; Paystack subscription id, event-id collisions, `not_renew` semantics); the code now fixes/tolerates them with regression tests, but the corrected mappings remain unverified against live traffic |
| Entitlements | client claims a plan; limits bypassed | plan read server-side from `plan_definitions` + subscription row on every gated action; limits (members, wallets, payouts/month, batch size, schedules, API keys, MFA, reports) enforced in services, not UI | `saas.itest` (limits per plan), E2E billing screens | plan numbers are **hypotheses**, configurable; no metering reconciliation against provider invoices (no live provider) |
| LNURL-pay / Lightning Address | SSRF, substituted invoice, wrong amount, open-ended hang | SSRF-safe fetch (https only, DNS pinned to vetted IP, IPv4/IPv6/mapped ranges refused, no redirects, size/time caps); response checked for `payRequest`, amount within min/max; callback invoice must match requested amount, **network**, be unexpired, and carry `h` = SHA-256 of the advertised metadata (LUD-06/16); payee node key surfaced to approver and still bound to the recipient by the existing destination-binding rule | `lnurl.itest`, `lnd.itest` (real LNURL-pay against regtest) | a malicious server can still return a valid invoice to **its own** node — Orynt shows the node key and binds it, it cannot know that node is the intended person. Name/domain is never treated as proof |
| Batch CSV payouts | formula injection into spreadsheets; oversized/duplicate rows; partial authorisation | export neutralises cells beginning `= + - @ \t \r` (non-numeric) with a leading `'`; import is a plain RFC 4180 parser with row-level validation and per-row errors (imported memo text is stored as given and neutralised only when exported); each row becomes an ordinary obligation that needs its own approval; batch-size entitlement | `saas.itest` (CSV) | no streaming parser for very large files (bounded by body limit) |
| Recurring obligations | silent authorisation bypass | a schedule only **creates drafts**; approval and policy checks run exactly as for manual payouts; cannot self-approve | `saas.itest` (schedules) | none known; a schedule creator who is also an approver is limited by the existing maker≠checker rule |
| Reports / exports | tenant data leakage; fiat shown as settlement | tenant-scoped queries; amounts reported in msat/sats with fiat only as labelled non-authoritative estimate | `saas.itest` | exports are downloadable by any role with `report:read`; no export audit alerting |
| Support / admin tooling | cross-tenant access by staff | tickets are tenant-scoped; no staff impersonation feature exists; any future admin tooling must be separately designed | `saas.itest` | **no internal admin console**; operations staff act through the database (high privilege, un-audited by the product) |
| Analytics | covert tracking / PII | in-product analytics store an event **name and org id only** (no user id, amounts or payee data) and never fail a request; the marketing-site contact form requires an explicit consent tick | `saas.itest` | the site-side analytics/telemetry behaviour is covered by the site agent's work and is **not** assessed here; privacy notice is an unreviewed draft |
| Rate limiting | credential stuffing | IP-keyed limits incl. tighter limits on sign-in/reset; static assets exempt | `security.itest` | in-memory, per process; behind a proxy `ORYNT_TRUST_PROXY` must be set correctly |

## Residual risks to carry into any launch decision
1. Wallet-credential blast radius is unchanged: Orynt enforces approvals; the wallet does not (see `threat-model.md`).
2. A fake LND endpoint plus a self-held preimage yields a "REAL" receipt; mitigated only by the explicit limitation text and a future managed-node allow-list.
3. Nothing here has been reviewed by a human security professional.
4. Live billing, live e-mail and production hosting are **uncommissioned**; their failure modes are unobserved.
